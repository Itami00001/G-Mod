# Отчёт о функциях и связях проекта GMod

## Обзор архитектуры

Проект GMod реализован по принципам Clean Architecture с разделением на слои:
- **Domain** - доменные сущности и интерфейсы
- **Use Cases** - сценарии использования
- **Infrastructure** - внешние зависимости
- **UI** - пользовательский интерфейс
- **Config** - конфигурация

## Подробное описание функций и связей

### 1. Слой Domain (Домен)

#### 1.1 Файл `src/gmod/domain/entities.py`

**Назначение:** Определение доменных сущностей проекта.

**Функции:**
- `Repository` - сущность репозитория Git
  - Поля: id, url, local_path, name, default_branch, created_at
  - Используется для хранения информации о репозиториях
  
- `Commit` - сущность коммита
  - Поля: hash, message, author, date, repo_id
  - Используется для хранения информации о коммитах
  
- `FileDiff` - сущность diff файла
  - Поля: file_path, old_content, new_content, commit_hash, repo_id, is_added, is_deleted, is_modified
  - Используется для хранения изменений в файлах
  
- `CodeUnit` - сущность единицы кода
  - Поля: unit_type, name, file_path, start_line, end_line, content, language, dependencies
  - Используется для хранения информации о функциях, классах, модулях
  
- `MetricResult` - результат вычисления метрики
  - Поля: metric_name, value, unit_type, unit_name, file_path, timestamp
  - Используется для хранения результатов метрик
  
- `AIReport` - сущность AI-отчёта
  - Поля: id, repo_id, commit_hash, agent_type, prompt, response_json, risk_score, timestamp
  - Используется для хранения AI-анализов

**Связи:**
- Используется во всех слоях приложения
- Импортируется в `infrastructure/git/git_parser.py`
- Импортируется в `infrastructure/parsers/`
- Импортируется в `infrastructure/metrics/`
- Импортируется в `usecases/analyze_repository.py`

#### 1.2 Файл `src/gmod/domain/interfaces.py`

**Назначение:** Определение интерфейсов для инфраструктуры.

**Функции:**
- `IGitParser` - интерфейс парсера Git
  - Методы: clone_repository, open_repository, get_commits, get_file_diff, get_branches
  
- `ILanguageParser` - интерфейс парсера языков
  - Методы: parse_file, get_dependencies
  
- `IMetric` - интерфейс метрики
  - Методы: compute, get_name
  
- `ILLMProvider` - интерфейс провайдера LLM
  - Методы: generate, is_available

**Связи:**
- Реализуется в `infrastructure/git/git_parser.py` (IGitParser)
- Реализуется в `infrastructure/parsers/` (ILanguageParser)
- Реализуется в `infrastructure/metrics/` (IMetric)
- Будет реализован в `infrastructure/llm/` (ILLMProvider)

### 2. Слой Infrastructure (Инфраструктура)

#### 2.1 Git парсер - `src/gmod/infrastructure/git/git_parser.py`

**Назначение:** Работа с Git репозиториями через gitpython.

**Функции:**
- `GitParser.__init__(diff_only)` - инициализация парсера
  - Параметр diff_only определяет режим анализа (только diff или файл целиком)
  
- `clone_repository(url, local_path)` - клонирование репозитория
  - Создаёт локальную копию удалённого репозитория
  - Возвращает сущность Repository
  
- `open_repository(local_path)` - открытие локального репозитория
  - Открывает существующий локальный репозиторий
  - Возвращает сущность Repository
  
- `get_commits(repo_id, limit, repo_path)` - получение коммитов
  - Возвращает список сущностей Commit
  - Опционально принимает путь к репозиторию для тестов
  
- `get_file_diff(repo_id, commit_hash, file_path)` - получение diff файла
  - Возвращает сущность FileDiff
  - Учитывает режим diff_only
  
- `get_branches(repo_id, repo_path)` - получение веток
  - Возвращает список названий веток
  
- `save_repository_info(repository)` - сохранение информации о репозитории
  - Сохраняет путь, URL и ветку в БД

**Связи:**
- Импортирует из `domain.entities` (Repository, Commit, FileDiff)
- Импортирует из `domain.interfaces` (IGitParser)
- Импортирует из `infrastructure.db.database` (get_database)
- Используется в `usecases/analyze_repository.py`

#### 2.2 Парсеры языков - `src/gmod/infrastructure/parsers/`

**Файл `base.py`:**
- `BaseLanguageParser` - базовый класс парсера
  - Методы: parse_file, get_dependencies, get_language
  
**Файл `python_parser.py`:**
- `PythonParser` - парсер Python кода
  - Использует tree-sitter если доступен, иначе regex
  - Методы: parse_file, _parse_with_tree_sitter, _parse_with_regex, get_dependencies
  
**Файл `factory.py`:**
- `ParserFactory` - фабрика парсеров
  - Методы: register_parser, get_parser, get_supported_languages, parse_file, detect_language

**Связи:**
- `base.py` импортирует из `domain.entities` (CodeUnit) и `domain.interfaces` (ILanguageParser)
- `python_parser.py` импортирует из `base.py`
- `factory.py` импортирует из `base.py` и все конкретные парсеры
- Используется в `usecases/analyze_repository.py`

### 3. Слой Use Cases (Сценарии)

#### 3.1 Файл `src/gmod/usecases/analyze_repository.py`

- `_analyze_file(repository, commit_hash, file_path)` - анализ файла
- `_save_metric(repo_id, commit_hash, metric)` - сохранение метрики
- `get_analysis_results(repo_id, commit_hash)` - получение результатов
- `get_metrics_summary(repo_id, commit_hash)` - получение сводки по метрикам

**Связи:**
- Импортирует из `domain.entities`
- Импортирует из `infrastructure.git.git_parser`
- Импортирует из `infrastructure.parsers.factory`
- Импортирует из `infrastructure.metrics.factory`

## Поток данных при анализе репозитория

1. **Инициализация:**
   - `main.py` → `setup_logging()` → создание логов
   - `main.py` → `MainWindow.__init__()` → восстановление состояния из БД

2. **Анализ репозитория:**
   - `AnalyzeRepositoryUseCase.execute()` → входная точка
   - `GitParser.open_repository()` → открытие репозитория
   - `GitParser.get_commits()` → получение коммитов
   - `GitParser.get_file_diff()` → получение diff файлов
   - `ParserFactory.parse_file()` → парсинг файлов
   - `PythonParser.parse_file()` → разбор на единицы кода
   - `MetricFactory.compute_all_metrics()` → вычисление метрик
   - `Database.save_metric()` → сохранение в БД с кэшированием

3. **Отображение результатов:**
   - `Database.get_analysis_results()` → загрузка из БД
   - `MainWindow` → отображение в UI

## Кэширование

Система кэширования реализована на уровне БД:
- Ключ кэша: `repo_id + commit_hash + file_path + unit_type + unit_name + metric_name`
- Проверка кэша перед вычислением метрики
- Автоматическое сохранение в кэш при вычислении

## Обработка ошибок

- Все метрики имеют `_safe_compute()` для обработки ошибок
- Git операции обернуты в try-except с логированием
- Парсеры имеют падбэк на regex если tree-sitter недоступен
- База данных использует контекстные менеджеры для автоматического rollback при ошибках
