# Метрики GMod и лабораторные работы — подробно

> Этот файл отвечает на вопросы: что из методичек реализовано в программе,
> какие метрики есть, **что каждая делает и как считается (формула)**,
> и где всё это находится в приложении.

## 2. Как вообще считается любая метрика в GMod

```
Код функции/класса (CodeUnit)
        ↓  MetricFactory.compute_all_metrics()
~50 классов, у каждого метод _compute_impl() → число float
        ↓  BaseMetric.compute() заворачивает в MetricResult
SQLite → raw_metrics(file, type, name, metric, value)
```

Важно:
- **Имя метрики в базе = имя класса**: `CyclomaticComplexity`,
  `LinesOfCode`, `FanOut`, `ChurnMetric` и т.д. (поэтому в таблицах
  английские названия).
- Почти всё считается **регулярными выражениями по тексту** (regex),
  а не полным разбором синтаксиса — быстро, но приблизительно.
- Парсер понимает **только Python** (tree-sitter, запасной — regex).
- Метрики, требующие весь проект (кому сколько должны), внутри одной
  функции посчитать нельзя — такие возвращают 0 (честно помечены ниже).

## 3. Каталог метрик с формулами

### 3.1. Сложность (`complexity.py`)

| Метрика (имя в БД) | Что показывает | Формула из кода |
|---|---|---|
| `CyclomaticComplexity` | Цикломатическая сложность Маккейба — число независимых путей | `1 + число слов if/elif/else/for/while/try/except/finally/with/and/or/?/:/case/lambda` в тексте. Порог тревожности в индустрии: **> 10** |
| `CognitiveComplexity` | Насколько тяжело понять код человеку (вложенность весит больше) | Каждое `if/for/while/...` добавляет **текущий уровень вложенности**; `and/or` добавляют `(уровень+1)`. Плоская цепочка дешевле глубокой |
| `NPathComplexity` | Число возможных путей выполнения | `2^(if+for+while+case) × (and+or+1)`. Растёт взрывообразно — главный детектор «не тестируемо» |
| `HalsteadVolume` | Объём программы V (лаба 5) | `V = (N1+N2) × log2(n1+n2)`, где n1/N1 — уникальные/все операторы, n2/N2 — уникальные/все операнды |
| `HalsteadDifficulty` | Трудность понимания D | `D = (n1/2) × (N2/n2)` |
| `HalsteadEffort` | Усилия на разработку E | `E = V × D` |
| `HalsteadBugs` | Прогноз числа ошибок | `B = V / 3000` |
| `MaintainabilityIndex` | Индекс поддерживаемости 0–100 (больше — лучше) | `MI = 171 − 5.2·ln(V) − 0.23·CC − 16.2·ln(LOC)`, обрезка в [0, 100]. Используется в лабе 5 как «уровень программы» |

### 3.2. Размер (`size.py`)

| Метрика | Формула из кода |
|---|---|
| `LinesOfCode` | Число непустых строк без `#`-комментариев |
| `FunctionLength` | Все строки функции (только для function, иначе 0) |
| `ParameterCount` | Параметры в скобках `def`, минус `self/cls/*args/**kwargs` |
| `ExitPointCount` | `return` + `break` + `continue` (идеал — 1 выход) |
| `NestingDepth` | Максимальная глубина if/for/while/try/def/class |

### 3.3. Связность (`coupling.py`) — тема лабы 1 (сцепление!)

| Метрика | Формула из кода |
|---|---|
| `FanIn` | Число **уникальных** вызовов `имя(` в тексте (без print/len/…); упрощение: показывает, сколько сущностей затрагивает юнит |
| `FanOut` | Уникальные `import X` + `from X import` + вызовы `модуль.метод(` |
| `Coupling` | `FanIn + FanOut` |
| `Cohesion` | `(переменные + функции + классы) / строки × 100`, максимум 100 |
| `AfferentCoupling` (Ca) | **Всегда 0** — требует анализа всего проекта, внутри функции не считается |
| `EfferentCoupling` (Ce) | Число уникальных импортов |
| `Instability` | `Ce / (Ca + Ce)` (0 — стабилен, 1 — нестабилен); при Ca=Ce=0 → 0 |
| `Abstractness` | 1, если в классе есть `ABC/abstractmethod/pass`, иначе 0 (только для class) |
| `DistanceFromMainSequence` | `D = |A + I − 1|` — расстояние до «идеального баланса» абстракции и стабильности |

### 3.4. ООП (`oop.py`)

| Метрика | Формула из кода |
|---|---|
| `CouplingBetweenObjects` (CBO) | Уникальные импорты + родители в `class X(...)` + аннотации типов (без str/int/…) |
| `ResponseForClass` (RFC) | Уникальные `def` + вызовы `self.метод(` |
| `LackOfCohesionOfMethods` (LCOM) | `max(0, P − Q)`, где P — пары методов **без** общих `self`-атрибутов, Q — с общими. 0 = класс целостный |
| `WeightedMethodsPerClass` (WMC) | Сумма «1 + if/elif/for/while/except» по каждому методу |
| `DepthOfInheritanceTree` (DIT) | Число родителей в `class X(A, B)` (запятые + 1), без наследования — 0 |
| `NumberOfChildren` (NOC) | **Всегда 0** — нужен весь проект |
| `ClassSize` | Методы + присваивания `self.x =` |
| `PublicMethodCount` / `PrivateMethodCount` | `def имя(` / `def _имя(` |

### 3.5. Комментарии (`comments.py`)

| Метрика | Формула из кода |
|---|---|
| `CommentDensity` | `строки с # / строки кода × 100` (%) |
| `CommentToCodeRatio` | символы комментариев / символы кода (с учётом `"""docstring"""`) |
| `DocumentationCoverage` | 1, если есть docstring/комментарий, иначе 0 (только function/class) |
| `CommentedOutCode` | Строки с `#`, содержащие символы кода (`= ( ) :` и т.п.) — мёртвый код |

### 3.6. Запахи кода (`code_smells.py`, индикаторы 0/1)

| Метрика | Порог из кода |
|---|---|
| `LongMethod` | 1, если функция **> 50 строк** |
| `LongParameterList` | 1, если параметров **> 7** |
| `LargeClass` | 1, если класс **> 300 строк или > 20 методов** |
| `DuplicatedCode` | % повторяющихся непустых строк (0–100) |
| `FeatureEnvy` | 1, если чужих `объект.метод(` более чем вдвое больше своих `self.` |
| `DataClumps` | Число повторяющихся пар соседних параметров |
| `PrimitiveObsession` | 1, если примитивов (`int/str/…`) среди аннотаций **> 80%** |
| `ShotgunSurgery` | **Всегда 0** — нужен весь проект |
| `GodClass` | 1, если выполнено ≥2 из 4: методов >20, атрибутов >10, внешних обращений >15, тем (database/file/network/…) >2 |

### 3.7. История Git (`vcs.py`)

| Метрика | Формула из кода |
|---|---|
| `ChurnMetric` | Число коммитов, где путь/имя файла встречается в сообщении (эвристика!) |
| `ChangeFrequency` | `churn / дни между первым и последним коммитом` |
| `RecentChanges` | Тот же churn, но по коммитам за последние 30 дней |
| `AuthorsCount` | Уникальные авторы таких коммитов |
| `CommitMessageQuality` | 0–4 балла за сообщение: длина 10–50 (+1), глагол add/fix/… (+1), >2 слов (+1), без «fix fix» (+1); среднее |
| `BugFixFrequency` | Коммиты со словами fix/bug/error/issue/patch/hotfix, связанные с файлом |

> ⚠️ Честная оговорка для защиты: VCS-метрики — **эвристика по текстам
> сообщений**, а не точный diff-анализ; без переданных коммитов дают 0.
> Это нормально указать как ограничение и направление развития.

## 4. Где метрики находятся в программе

| Место | Что видно |
|---|---|
| Вкладка **«Метрики»** | Главная таблица: Файл \| Тип \| Имя \| Метрика \| Значение \| Время; фильтры по файлу/типу/метрике/поиск; экспорт CSV/JSON; кнопка «Обновить»; статусы «в обработке / рассчитаны / не получилось» |
| Вкладка **«Анализ» → «Функции»** | Таблица Файл \| Функция \| Метрика \| Значение по выбранным файлам/папкам + словесный разбор LLM |
| Вкладка **«Граф»** | Цвет узлов по метрике (сложность/LOC/Fan-out/Churn/MI); клик — min/avg/max по файлу |
| Вкладка **«Анализ» → прогноз** | Тренд средних метрик по коммитам + прогноз LLM + вердикт валидатора |
| Вкладка **«Чат» → «Что отправлено AI»** | Какие метрики реально ушли нейросети: total/by type/avg/top/outliers + сырые значения |
| Валидатор и MLP | Метрики — входные признаки: валидатор берёт 5 чисел, MLP — 8 (`CyclomaticComplexity, CognitiveComplexity, MaintainabilityIndex, LinesOfCode, FanIn, FanOut, ChurnMetric, CommentDensity`) |
| БД | Таблица `raw_metrics`; сводки — `AnalyzeRepositoryUseCase.get_metrics_summary()` |
| Код | `src/gmod/infrastructure/metrics/*.py`, фабрика — `factory.py` (`compute_all_metrics`), вызов — `usecases/analyze_repository.py` |

## 5. Что сказать на защите (шпаргалка)

1. **Холстед реализован** (V/D/E/Bugs + MI) — покрывает лабу 5.
2. **Маккейб реализован** как `1 + число ветвлений` — покрывает лабу
   Джилба–Маккейба (сам Джилб CL/CLI и Чепин — нет, назвать следующим шагом).
3. **Связность/сцепление из лабы 1** измеряются: FanIn/FanOut/Coupling/CBO/LCOM.
4. Значения в БД — вещественные числа + кэш (повторный расчёт не дублируется).
5. Ограничения (назвать честно): только Python, regex вместо AST,
   проектные метрики Ca/NOC/Shotgun = 0, VCS — эвристика.
6. Нейросеть использует метрики как признаки и объясняет их словами —
   это и есть «AI-анализ кода с визуализацией метрик» из темы проекта.
