# Отчёт о применении методических материалов

## Применение материалов из Lab1.txt (Модульное программирование. Метод нисходящего программирования)

### 1. Модульное программирование

**Теория из методички:**
- Модульное программирование – это способ разработки программ по частям, которые называются программными модулями
- Модуль – логически законченная часть программы, выполняющая определённую функцию
- Характеристики модуля: один вход и один выход, функциональная завершенность, логическая независимость, слабые информационные связи

**Применение в проекте:**
- Проект разделён на модули по Clean Architecture:
  - `domain/` - модуль доменных сущностей
  - `usecases/` - модуль сценариев использования
  - `infrastructure/` - модуль внешних зависимостей
  - `ui/` - модуль пользовательского интерфейса
  - `config/` - модуль конфигурации

**Примеры реализации:**
- `src/gmod/domain/entities.py` - модуль сущностей с одним входом (импорт) и одним выходом (экспорт классов)
- `src/gmod/infrastructure/metrics/` - каждый файл метрики является отдельным модулем с функциональной завершённостью
- `src/gmod/ui/main_window.py` - модуль UI с логической независимостью от бизнес-логики

### 2. Связность и сцепление модулей

**Теория из методички:**
- Связность модуля – степень его внутренних связей
- Сцепление модуля – степень его зависимости по данным от других модулей
- Рекомендуется использовать функционально связанный модуль и параметрическое сцепление

**Применение в проекте:**
- **Высокая связность внутри модулей:**
  - В `domain/entities.py` все сущности связаны общей целью (моделирование предметной области)
  - В `infrastructure/metrics/complexity.py` все метрики сложности связаны общей темой
  
- **Слабое сцепление между модулями:**
  - `domain/` не зависит от `infrastructure/` (Clean Architecture)
  - `ui/` зависит только от интерфейсов `domain/`
  - Обмен данными через параметры (параметрическое сцепление)

**Примеры реализации:**
```python
# domain/entities.py - функциональная связность
@dataclass
class Repository:
    """Сущность репозитория - одна функция"""
    id: str
    url: str
    # ...

# infrastructure/metrics/factory.py - параметрическое сцепление
def compute_metric(name: str, unit: CodeUnit, **kwargs):
    """Данные передаются через параметры"""
    metric = self.get_metric(name, **kwargs)
    return metric.compute(unit)
```

### 3. Метод нисходящего программирования

**Теория из методички:**
- Метод нисходящего программирования базируется на методе пошаговой детализации
- Сначала строится структурная схема, затем реализуется модуль высочайшего уровня
- Модули следующего уровня заменяются фиктивными функциями – заглушками
- Заглушка обычно печатает сообщения типа: «Такая-то функция была вызвана»

**Применение в проекте:**
- **Этап 1 (Prompt1):** Создан скелет приложения с заглушками
  - Главное окно с UI (верхний уровень)
  - Кнопки с заглушками: `load_repository`, `send_message`, `gmod_button`
  - Вкладки с заглушками: "Метрики (заглушка)", "Граф (заглушка)"
  
- **Этап 2 (Prompt2):** Замена заглушек реальной логикой
  - Реализован `GitParser` вместо заглушки загрузки репозитория
  - Реализованы парсеры и метрики вместо заглушек анализа
  - Реализован `AnalyzeRepositoryUseCase` вместо заглушки обработки

**Примеры заглушек из Prompt1:**
```python
# src/gmod/ui/main_window.py - заглушки первого этапа
```

### 4. Структурное программирование

**Теория из методички:**
- Структурное программирование – методология создания программ на основе иерархической структуры блоков
- Базовые конструкции: следование, выбор, повторение
- Цель: получение программы простой структуры

**Применение в проекте:**
- **Следование:** Последовательное выполнение операций в метриках
```python
# infrastructure/metrics/complexity.py
def _compute_impl(self, unit: CodeUnit) -> float:
    content = unit.content
    complexity = 1  # Базовая сложность
    # Следование операций
    for keyword in complexity_keywords:
        complexity += len(re.findall(keyword, content))
    return float(complexity)
```

- **Выбор:** Условные конструкции в парсерах
```python
# infrastructure/parsers/python_parser.py
if self.parser and self.language:
    units = self._parse_with_tree_sitter(file_path, content)
else:
    units = self._parse_with_regex(file_path, content)
```

- **Повторение:** Циклы для обхода деревьев и списков
```python
# infrastructure/metrics/factory.py
for metric in metrics:
    try:
        result = metric.compute(unit)
        results.append(result)
```

### 5. Пошаговая детализация

**Теория из методички:**
- Суть метода: разбиение задачи на ряд подзадач
- На первом шаге описывается общая схема, затем детализируется
- Преимущества: сохраняется концептуальная целостность, параллельная разработка

**Применение в проекте:**
- **Декомпозиция задачи анализа репозитория:**
  1. Открыть репозиторий → `GitParser.open_repository()`
  2. Получить коммиты → `GitParser.get_commits()`
  3. Найти изменённые файлы → `_get_changed_files()`
  4. Парсить файлы → `ParserFactory.parse_file()`
  5. Вычислить метрики → `MetricFactory.compute_all_metrics()`
  6. Сохранить результаты → `Database.save_metric()`

- **Декомпозиция метрик:**
  1. Базовый класс → `BaseMetric`
  2. Категории → complexity, size, coupling, oop, comments, code_smells, vcs
  3. Конкретные метрики → `CyclomaticComplexity`, `LinesOfCode`, и т.д.

## Применение материалов из Lab2.txt (Модульное программирование. Метод восходящего программирования)

### 1. Метод восходящего программирования

**Теория из методички:**
- Метод восходящего программирования использует противоположную стратегию
- Программа создается путем объединения простых программных компонентов
- Сначала реализуются компоненты самого низкого уровня
- Для тестирования создаются программы-драйверы

**Применение в проекте:**
- **Восходящий подход для инфраструктуры:**
  1. Сначала реализованы базовые классы: `BaseMetric`, `BaseLanguageParser`
  2. Затем конкретные реализации: `CyclomaticComplexity`, `PythonParser`
  3. Затем фабрики: `MetricFactory`, `ParserFactory`
  4. Затем use case: `AnalyzeRepositoryUseCase`
  5. Затем интеграция с UI

- **Комбинированный подход:**
  - UI разработан нисходящим методом (скелет → детали)
  - Инфраструктура разработана восходящим методом (базовые компоненты → сложные системы)

### 2. Тестовые драйверы

**Теория из методички:**
- Тестовый драйвер – скелетная модель модуля для тестирования
- Содержит минимум кода для вызова тестируемого модуля
- Используется для имитации работы модуля более высокого уровня

**Применение в проекте:**
- **Тесты как драйверы для низкоуровневых модулей:**
  - `tests/test_metrics.py` - драйвер для тестирования метрик
  - `tests/test_parsers.py` - драйвер для тестирования парсеров
  - `tests/test_git_parser.py` - драйвер для тестирования Git парсера

**Пример тестового драйвера:**
```python
# tests/test_metrics.py
@pytest.fixture
def sample_function_unit():
    """Фикстура для примера функции - драйвер данных"""
    return CodeUnit(
        unit_type="function",
        name="test_function",
        file_path="test.py",
        start_line=1,
        end_line=10,
        content="def test_function(arg1, arg2): ...",
        language="python"
    )

def test_cyclomatic_complexity(sample_function_unit):
    """Тест как драйвер для проверки метрики"""
    metric = CyclomaticComplexity()
    result = metric.compute(sample_function_unit)
    assert result.value > 1
```

### 3. Указатели на функции (аналог в Python)

**Теория из методички:**
- Указатели на функции часто используются в качестве аргументов других функций
- Создаются универсальные функции, упрощающие текст сложной программы

**Применение в проекте:**
- **Аналог указателей на функции в Python:**
  - Фабрики используют классы как "указатели" на реализации
  - Словари с классами как аналоги массивов указателей

**Пример реализации:**
```python
# infrastructure/metrics/factory.py - аналог указателей на функции
_metrics: Dict[str, Type[BaseMetric]] = {
    "cyclomatic_complexity": CyclomaticComplexity,
    "maintainability_index": MaintainabilityIndex,
    # ...
}

def get_metric(cls, name: str, **kwargs):
    """Аналог вызова функции через указатель"""
    metric_class = cls._metrics.get(name.lower())
    if metric_class:
        return metric_class(**kwargs)  # Вызов через "указатель"
```

## Комбинированный подход в проекте

**Теория из методички:**
- На практике более эффективным считается комбинированный подход
- Общие модули разрабатываются восходящим методом
- Остальная часть программы - нисходящим принципом

**Применение в проекте:**
- **Восходящий подход для общих модулей:**
  - Базовые классы (`BaseMetric`, `BaseLanguageParser`)
  - Фабрики (`MetricFactory`, `ParserFactory`)
  - Утилиты (`Database`, логирование)
  
- **Нисходящий подход для специфичных модулей:**
  - UI (`MainWindow` - скелет → детали)
  - Use cases (`AnalyzeRepositoryUseCase` - сценарий → реализация)
  - Интеграция компонентов

**Пример комбинированного подхода:**
